<h2>一、试用前 24 小时：把要测的指标写下来</h2>
<p>很多人试用第一天随手点几下，第二天忙起来就忘了，第七天要决定的时候没有任何数据。开工前花十分钟，在表格里写好四行：延迟、丢包、夜间波动、切换接管时间。写下来之后再测，避免中途改标准——标准一改，数据就废了。</p>
<h3>四个指标定死，中途别改</h3>
<p>延迟取三次测量的中位数，不看单次；丢包用持续一分钟的 ping 统计；夜间波动取晚八点到十一点与下午三点两个时段的中位数比值；切换接管时间从触发到业务恢复计。四个指标都能用命令行拿到，不需要额外工具。</p>

<h2>二、T0 到 T+2 小时：开通与首轮自测</h2>
<p>开通后两小时内完成首轮自测，这一步决定要不要继续。重点不是跑分，而是确认这条线是不是你说的那条：城市对不对、运营商对不对、是不是住宅段。三项有一个不对，立刻联系服务商，别自己想办法绕。</p>
<h3>首轮自测清单</h3>
<p>一，curl 打 ipinfo，看 city、region、org 三字段；二，ping 目标站点六十秒，记丢包与平均延迟；三，浏览器打开目标业务，完成一次正常登录操作；四，dig 查一次解析落地，确认与出口同区域；五，读一次时区与语言，确认与出口城市匹配。五项十分钟内能跑完。</p>

<h2>三、T+24 到 T+72 小时：晚间时段与切换演练</h2>
<p>共享 IP 最典型的问题是晚上变慢，白天怎么测都测不出来。所以试用必须覆盖至少两个晚间高峰，否则测的是假象。这三天还要把备用线的切换演练做一次，光看介绍不算。</p>
<h3>晚间高峰必须单独测</h3>
<p>晚上八点到十一点，用同一组命令再测一次，把结果和下午的数据放在一起比。判断标准：延迟上浮不超过 40%，丢包不超过 3%。超过这个范围说明这条线在高峰期与他人抢带宽，共享线的常见表现，独享线不该这样。</p>
<h3>切换演练怎么做才真实</h3>
<p>不要用「把主线下线」的方式演练，那是极端场景。真实做法是人为让主线的探测连续失败三次，看系统是否在预定时间内切到备用，并观察正在进行的会话有没有中断、重连后是否回到同一状态。演练记录写下三个时间点：触发时刻、切换完成时刻、业务恢复时刻。</p>

<h2>四、第七天：转正还是退掉</h2>
<h3>满足什么条件才转包月</h3>
<p>四条同时满足：延迟与丢包在标准内、晚间波动不超过 40%、切换接管在 60 秒内且会话可恢复、七天里没有出现两次以上额外验证。四条缺一条，先按量续一周再看，别急着签长约。</p>
<h3>退掉时怎么收尾</h3>
<p>三件事：把试用期间的出口 IP 与测速数据归档，下次选型时能对比；把账号迁回原线路时按低强度用三天，别当天就恢复全量；确认试用账号下的会话与日志已清理，凭据已失效。收尾干净，下次换回来才不会带着上次的残留。</p>
<h3>试用期最该记的一个数字</h3>
<p>不是峰值速度，是「平均每天出现几次不顺畅」。这个数字最贴近真实体验：一周里如果每天有一两次明显卡顿，即便测速数据漂亮，实际使用也难受。记录下来，比任何参数都直观。</p>

<h2>常见问答</h2>
<h3>试用只有两小时，够判断吗？</h3>
<p>答：够判断可用性，不够判断稳定性。两小时能确认城市、ASN、连通性；晚间波动和切换能力必须拉长时间。只有两小时的话，至少把时段选在晚八点。</p>

<h3>备用线平时要不要一直开着？</h3>
<p>答：按量计费下不必常开，但要保证能在一分钟内启用。每周演练一次切换，确认阈值配置没被改过，比长期空跑更有意义。</p>

<h3>试用期出现一次额外验证，要不要直接放弃？</h3>
<p>答：看次数和场景。七天里一次、且发生在切换之后，属于正常波动；三天两次以上、且与切换无关，说明线路或环境有问题，建议换线。</p>

<h3>换了稳定线之后，原来的共享线还有用吗？</h3>
<p>答：可以留作低频备用，比如演示、临时抓取。别把重要账号留在上面，共享线的波动不可控，出问题时也没有责任方可以追。</p>
